# Майнинг для опытных

Большинству майнеров эта страница не нужна: [быстрый старт](/docs/miner#quick-start) описывает одно устройство, которое обслуживает одного оператора. Читайте дальше, если хотите обслуживать всех операторов, запускать несколько выходных узлов с одного хоста, автоматизировать получение вознаграждений или управлять большим флотом. Если вы использовали установщик, пишите `urnetwork` везде, где на этой странице написано `provider`.

## Майнинг для всех операторов из списка

`provider provide --all-operators` майнит для всех операторов из списка, опубликованного на [ur.xyz/operators.yml](/operators.yml), по одному процессу майнера на оператора. Проще всего — входить к каждому оператору с **hotkey** Bittensor, как с кошельком TAO:

```bash
provider provide --all-operators --auto-register --hotkey_seed_file=/absolute/private/hotkey.seed
```

Никаких транзакций в цепочке при этом нет. Первый вход создаёт сеть hotkey у этого оператора, и каждый новый оператор регистрирует первое устройство: `--auto-register` подразумевает `--allow-client-registration`, который никогда не заменяет идентичность, уже имеющуюся у майнера. Файл seed содержит 32-байтный seed sr25519 этого hotkey, в необработанном виде или как 64 шестнадцатеричных символа, в закрытом файле, который майнер никогда не создаёт сам.

Чтобы вместо этого входить к операторам самостоятельно, выведите их список, затем войдите к каждому с кодом авторизации, логином аккаунта или hotkey:

```bash
provider operators
provider auth --operator='<domain>'
provider auth --operator='<domain>' --user_auth='you@example.com'
provider auth --operator='<domain>' --hotkey_seed_file=/absolute/private/hotkey.seed
```

`provider operators` выводит, откуда взят список, и его дайджест, а затем для каждого оператора — домен, состояние входа (`jwt present` или `awaiting auth`), URL API и URL подключения. `provider auth --operator` запрашивает код или пароль, которые вы не передали, и сохраняет вход для этого оператора в `~/.urnetwork/operators/<domain>/jwt`. У оператора, к которому вы вошли таким способом, ещё нет устройства, поэтому первому запуску нужен флаг регистрации; последующим — нет:

```bash
provider provide --all-operators --allow-client-registration
```

Оператор без входа не получает майнера. В журнале появляется `operator <domain> is awaiting auth: provider auth --operator=<domain>`, и майнер проверяет снова каждые пять минут.

### Как это работает

С `--all-operators` один процесс управляет майнером для каждого оператора из списка:

- У каждого оператора своя папка, `~/.urnetwork/operators/<domain>/`, со своим входом, ключом идентичности и учётными данными устройства. Это новые идентичности устройств: идентичность для одного оператора в `~/.urnetwork` не используется, а оператор, выбранный через `provider network use`, не применяется.
- Список загружается заново каждый час. `--operators-refresh=<duration>` меняет это — длительность в формате Go не меньше `1m`, например `30m`, — а `--operators-url=<url>` указывает на другой список. Последняя исправная копия хранится как `~/.urnetwork/operators.yml`, так что майнинг продолжается, пока ur.xyz недоступен.
- Новый оператор в списке получает майнер, как только для него выполнен вход, а майнер оператора, у которого изменились URL-адреса, перезапускается. Майнер оператора, исключённого из списка, получает SIGTERM, а через 60 секунд — SIGKILL; его папка сохраняется.
- Завершившийся майнер перезапускается через 30 секунд, с удвоением интервала до 10 минут. Ctrl-C или сигнал завершения останавливает все майнеры.
- `--max-memory` делится поровну между майнерами, и майнер перезапускается, когда его доля меняется. `--port` отдаёт состояние всех операторов; сами майнеры работают без порта состояния.
- Первый процесс майнера, занявший TCP-порт 443, обслуживает экстендер для всего хоста.
- `--all-operators` не принимает `--api_url`, `--connect_url`, `--provider-jwt`, `--wallet` и его флаги подписи, `--test-egress-source-ip`, а также флаги захвата и отчётов о закрытии — они остаются для одного оператора.

Чтобы запускать это как [собственную службу](/docs/miner/run#a-service-of-your-own), используйте `ExecStart=%h/.local/bin/provider provide --all-operators --auto-register --hotkey_seed_file=/absolute/private/hotkey.seed`. В автоматическом режиме служба сохраняет `--auto-register`, так что каждый новый оператор в списке регистрирует первое устройство; идентичность, уже имеющуюся у майнера, это никогда не заменяет. Если вы входите к операторам сами, уберите `--auto-register`, оставьте `--hotkey_seed_file`, если используете описанную ниже выплату через hotkey, и добавляйте `--allow-client-registration` только для первого запуска после входа к новому оператору.

### Одна подпись для всех операторов из списка

С `--all-operators` одна подпись coldkey задаёт кошелёк для выплат у всех операторов. И coldkey, и hotkey подписывают одно глобальное заявление, которое связывает hotkey с coldkey; оно хранится в виде цепочки в `~/.urnetwork/hotkey-wallet/`. Каждый оператор, к которому выполнен вход, затем хранит эту цепочку, и один только hotkey подписывает там делегирование вашей сети последней записи цепочки. Coldkey никогда не подписывает для каждого оператора отдельно.

Запросите заявление:

```bash
provider wallet hotkey challenge '<coldkey_ss58>' \
  --hotkey_seed_file=/absolute/private/hotkey.seed
```

Подпишите выведенное заявление в точности как есть этим coldkey, в том же контексте sr25519 `substrate`, что и для [обычного кошелька](/docs/miner/rewards#set-your-payout-wallet), затем выполните команду `wallet hotkey set`, которую выведет challenge. Она выглядит так:

```bash
provider wallet hotkey set '<coldkey_ss58>' \
  --hotkey_seed_file=/absolute/private/hotkey.seed \
  --message='<exact printed statement>' \
  --signature='0x<64-byte sr25519 signature>'
```

Заявление ждёт в `hotkey-wallet/pending.json`, пока его не зададут или не заменят. Если вы сознательно храните seed coldkey на этом компьютере, передайте `set` параметр `--coldkey_seed_file=/absolute/private/coldkey.seed` вместо `--message` и `--signature`.

`set` добавляет подпись hotkey, дописывает новую запись в цепочку, затем сохраняет цепочку и делегирование у каждого оператора, к которому выполнен вход, и сообщает о каждом; сбой у одного оператора никогда не останавливает остальных. `provider provide --all-operators` с `--hotkey_seed_file` поддерживает делегирование у каждого оператора, к которому выполнен вход, — при запуске и каждый час, включая операторов, добавленных в список позже, — так что coldkey подписывает только один раз. `provider wallet hotkey status` показывает цепочку, ожидающее заявление, если оно есть, и делегирование у каждого оператора.

Если эпохи не выбраны через `--wallet-from-epoch` и `--wallet-through-epoch`, первая запись зарабатывает начиная с эпохи 0, а следующие — с текущей эпохи операторов плюс 1. Каждое делегирование начинается с текущей эпохи оператора плюс 2, и каждый диапазон охватывает 65 536 эпох. Следующая запись меняет coldkey или эпохи.

Оператор платит устройству в таком порядке приоритета: собственный кошелёк устройства (`provider wallet set`), затем кошелёк на уровне сети, затем делегирование через hotkey.

### Получение вознаграждений у всех операторов

Каждый оператор проводит расчёты по своему пулу, поэтому забирайте вознаграждения у каждого оператора отдельно. Выберите учётные данные устройства этого оператора и его URL API, как их выводит `provider operators`:

```bash
provider claim --epoch='<settlement_epoch>' --rpc='https://<evm-json-rpc>' \
  --provider-jwt="$HOME/.urnetwork/operators/<domain>/.provider.jwt" \
  --api_url='<operator api_url>'
```

## Несколько выходных узлов на одном хосте

Майнер поддерживает выходные узлы SOCKS5, с отдельным устройством для каждого адреса прокси:

```bash
provider proxy add '<host>:<port>:<user>:<pass>'
provider proxy add --proxy_file=/absolute/private/proxies.txt
provider provide --allow-client-registration
```

Используйте флаг регистрации, только когда добавляете действительно новые выходные узлы; обычные перезапуски выполняются через `provider provide`. Каждый выходной узел хранит `.provider-<hash>.jwt` и свои вспомогательные файлы регистрации. Выбирайте этот файл через `--provider-jwt`, когда задаёте для узла кошелёк и забираете вознаграждения. Общий `.provider.key` и файлы всех выходных узлов должны входить в одну и ту же резервную копию. Значение имеют различные маршрутизируемые выходные узлы: добавление аккаунтов за тем же выходным узлом не увеличивает охват.

`provider proxy remove` удаляет выходные узлы, а `provider proxy auth add` и `provider proxy auth remove` управляют учётными данными прокси; см. `provider proxy --help`. С `--all-operators` файл `proxy` из `~/.urnetwork` копируется в папку каждого оператора при запуске его майнера.

## Автоматическое получение вознаграждений

### Отправка заявок с другого компьютера

Чтобы ключ relayer не хранился на майнере, проверьте заявку на майнере через `provider claim`, затем отправьте её точные данные заявки и адрес хранилища с другого компьютера через `snclaim`. Соберите его из того же исходного кода:

```bash
# From sn/:
go build -o "$HOME/.local/bin/snclaim" ./cli/snclaim
```

Или скачайте его из того же выпуска: на [странице выпусков](https://github.com/urnetwork/build/releases) также есть `urnetwork-snclaim-<version>.tar.gz` с `<os>/<arch>/snclaim` для Linux и macOS. Установите его так же, как в разделе [Загрузка вручную](/docs/miner/install#manual-download) устанавливается майнер. Затем:

```bash
snclaim submit --calldata='0x<verified claim calldata>' \
  --contract='0x<settlement vault>' --rpc='https://<evm-json-rpc>' \
  --chain_id=964 --key_file=/absolute/private/relayer.key --dry-run
```

Укажите фактический ID цепочки вашего развёртывания и уберите `--dry-run`, чтобы отправить. Отправляющему компьютеру всё равно нужно подключение к RPC. Чтобы узнать, была ли заявка уже принята:

```bash
snclaim status --epoch='<settlement_epoch>' --no_id='<operator id>' \
  --coldkey='<coldkey_ss58>' --contract='0x<settlement vault>' \
  --rpc='https://<evm-json-rpc>'
```

### Демон получения

Демоны получения работают только в Linux и macOS. Демон получения хранит ожидающие и подписанные заявки в долговечной очереди и отслеживает их результаты в цепочке EVM даже после перезапусков. Его конфигурация — строгий YAML:

```yaml
schema_version: 1
release: "1.0"
api_url: https://api.example.net
rpc:
  - https://evm-rpc.example.net
key_file: /home/miner/.urnetwork/private/relayer.key
jwt_file: /home/miner/.urnetwork/.provider.jwt
state_dir: /var/lib/urnetwork/claims/provider-1
poll_seconds: 30
lookback_epochs: 2
```

Замените эти пути и конечные точки. Относительные пути к файлам разрешаются относительно файла конфигурации. `jwt_file` выбирает учётные данные устройства и должен быть закрытым обычным файлом; если его не указать, выбирается `.provider.jwt` по умолчанию. `poll_seconds` принимает значения от 5 до 3 600; глубина просмотра по умолчанию — две эпохи, максимум 256.

Перед запуском подготовьте хранилище очереди заявок и получите точное объявление долговечного тома и его проверенный дайджест для хоста. Текущий допуск хранилища требует их; пустой папки или отсутствия флагов недостаточно. Объявление использует схему тома демона и охватывает фактические `state_dir` и очередь. См. инструкции о [владении очередью заявок](https://github.com/urfoundation/sn/blob/main/miner/CLAIM-QUEUE-OWNERSHIP.md) и о [подготовке хранилища офлайн](https://github.com/urfoundation/sn/blob/main/mainnet/OWNER-CUSTODY-PREPARATION.md).

```bash
provider claim-daemon --config=/absolute/path/claim.yml \
  --durable-volumes=/absolute/path/reviewed-daemon-volumes.json \
  --durable-volumes-sha256='sha256:<reviewed digest>'
```

Запускайте один демон на каждую очередь и ключ relayer и не отправляйте одновременно с этим ключом разовые заявки и не запускайте другой демон. После прерванной отправки сохраняйте всю папку очереди, включая вспомогательные файлы. Для записи очереди с пометкой `uncertain` нужно сверить её исходную подписанную транзакцию. Финализированная запись заявки показывает, что заявка принята; события оплаты отличают выплаченные вознаграждения от отложенных сумм.

Для счетов расчётов v2 `provider claim-daemon-v2` забирает средства со счёта, как только доступный для получения баланс достигает `--threshold-rao` (по умолчанию 1,9 α), а `--claim-now` один раз при запуске забирает всё, что доступно. `--v1-config` запускает описанный выше демон v1 в том же процессе с одним общим ключом relayer. Параметры см. в `provider claim-daemon-v2 --help`.

## Собственный UID майнера (верхний уровень)

По умолчанию каждый майнер зарабатывает в **пуле** своего оператора: выплата идёт на UID пула оператора, и пул делится между его устройствами. Большой флот может вместо этого получить **собственный UID майнера** в подсети. Тогда валидаторы взвешивают этот UID напрямую, а цепочка платит ему нативно — как α, застейканные на собственном hotkey флота под его собственным coldkey, — каждый tempo. В цепочке выплат нет ни пула, ни оператора, ни заявок.

### Кто может его получить

Валидаторы дают вес только **200 ведущим флотам**; UID любого другого флота не получает ничего. Флоты ранжируются по **широте маршрутизируемых выходных адресов**, а не по трафику:

- Каждый выходной адрес, через который валидатор проводит реальный проверочный узел, сводится к своему сетевому префиксу (/29 для IPv4, /48 для IPv6). Оценка флота — число различных префиксов, с которых выходят его устройства.
- Префикс, общий с другими флотами верхнего уровня, делится между ними поровну, так что много устройств за одним адресом или в одном небольшом диапазоне считаются один раз.
- Оценка сглаживается во времени (каждый tempo учитывается на четверть), поэтому одно неудачное измерение не роняет флот, а новому флоту нужно время, чтобы выйти на полную оценку.

Одно домашнее подключение считается примерно за один префикс. Собственный UID верхнего уровня окупается для флотов, устройства которых выходят из множества разных сетей, например для хостов, разбросанных по многим дата-центрам или по многим домашним подключениям.

Чтобы узнать своё положение, откройте на ur.io страницу **Top 200**: она показывает ориентировочную оценку и место вашего аккаунта относительно порога, а также привязаны ли уже ваши устройства к hotkey.

### Сколько это стоит и какие есть риски

- **Регистрация сжигает α.** Coldkey флота платит текущую плату за регистрацию в подсети (эта плата сжигается), и каждая новая регистрация повышает плату за следующую. `provider fleet register` показывает текущую сумму сжигания, прежде чем что-либо подписать.
- **UID ограничены.** Когда подсеть заполнена, новая регистрация вытесняет UID с наименьшей эмиссией, как только у этого UID закончится период иммунитета. Флот, выпавший из 200 ведущих, ничего не зарабатывает, вытесняется следующей регистрацией и должен снова заплатить сжигаемую плату за регистрацию, чтобы вернуться.
- **Только один уровень одновременно.** Устройство, привязанное к флоту верхнего уровня, не получает долю пула, пока привязка активна. Если флот теряет свой UID, его устройства снова зарабатывают в пуле своего оператора. Уже заработанные устройством вознаграждения пула остаются доступными для получения.
- **Привязка публична.** Привязка публикует, какие устройства принадлежат вашему hotkey, а значит, и сетевые префиксы, с которых они выходят. Устройства в пуле не связываются с вами таким образом.

### Как его получить

Вам понадобятся coldkey Bittensor с достаточным количеством TAO для сжигания, hotkey для флота и файлы идентичности майнеров (`~/.urnetwork`). Храните coldkey на одном компьютере для регистрации; майнерам нужны только их собственные идентичности. Регистрация, публикация, привязка и отзыв в mainnet работают только в Linux и macOS.

1. **Составьте манифест флота.** В нём указываются ID цепочки сети, netuid и координатор, ID флота, hotkey флота, поколение, а также ID клиента и открытый ключ каждого устройства. `provider fleet init` собирает его из файлов майнеров, а `provider fleet manifest --manifest=<path>` проверяет.
2. **Зарегистрируйте UID.** Выполните `provider fleet register` с манифестом, файлами seed hotkey и coldkey и конечными точками `--substrate`. Без `--apply` это пробный запуск, который называет текущую сумму сжигания и комиссию. Добавьте `--apply`, чтобы подписать и разослать транзакцию, с ограничениями `--burn_limit_rao` и `--fee_limit_rao`: цепочка отклонит регистрацию, которая сожгла бы больше вашего лимита.
3. **Опубликуйте манифест.** `provider fleet publish` записывает хеш манифеста в цепочку от имени hotkey флота.
4. **Привяжите каждое устройство к hotkey.** Каждую привязку подписывают и ключ устройства, и hotkey флота, так что никто не может присвоить себе устройства, которыми не управляет. Привязка начинается не раньше следующей эпохи и охватывает выбранный вами диапазон эпох (`--valid_from_epoch`, `--valid_to_epoch`). Либо:
   - выполните `provider fleet sign` для каждого устройства — команда только читает локальные файлы, — затем вставьте её вывод на странице Top 200 на ur.io и отправьте подготовленную ею транзакцию из своего EVM-кошелька; либо
   - выполните `provider fleet bind` для каждого устройства — команда сама отправляет привязку с ключом relayer для EVM и конечными точками `--rpc`.
5. **Проверяйте и поддерживайте.** `provider fleet status` показывает привязку устройства и UID. `provider fleet revoke` удаляет устройство начиная с будущей эпохи. Новые устройства привязывайте так же, а привязку обновляйте до её последней эпохи.

В mainnet для `register`, `publish`, `bind`, `status` и `revoke` также нужен проверенный документ полномочий среды выполнения флота сети (`--mainnet-runtime-authority` и его `--mainnet-runtime-authority-sha256`), а для операций записи — объявление долговечного тома (`--durable-volumes` и `--durable-volumes-sha256`). Все параметры описаны в [контракте полномочий и восстановления флота](https://github.com/urfoundation/sn/blob/main/miner/FLEET-MAINNET-RUNTIME.md) и в `provider fleet --help`. Как оцениваются верхний уровень и уровень пулов, описано в [whitepaper](https://github.com/urfoundation/sn/blob/main/WHITEPAPER.md), разделы 8.4 и 11.4.
