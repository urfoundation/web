# تشغيل موسِّع

الموسِّع مُرحِّل يتيح للناس الوصول إلى الشبكة من أماكن تُحجب فيها خوادم المشغّل نفسه. يشغّل كل مُعدِّن موسِّعًا بجانب نقطة خروجه، وهو مفعّل افتراضيًا. لا يعمل إلا عندما يستطيع الإنترنت الوصول إلى حاسوبك على منفذ TCP رقم 443. إن استخدمت مُثبِّتًا، فاكتب `urnetwork` حيثما تقول هذه الصفحة `provider`.

الموسِّع طرف في كل عقد يعبره، لذا يكسب حصة من كل عقد ينقله.

## المنافذ

افتح هذه المنافذ للاتصالات الواردة من أي عنوان، على IPv4 وعلى IPv6:

| المنفذ | البروتوكول | الحاجة | الغرض منه |
| --- | --- | --- | --- |
| 443 | TCP | مطلوب | الناقل الرئيسي للموسِّع. من دونه يبقى الموسِّع متوقفًا، ويحاول المُعدِّن المنفذ مجددًا كل 3 دقائق. |
| 443 | UDP | موصى به | ناقل QUIC. |
| 4053 | UDP | موصى به | ناقل DNS. |
| 53 | UDP | اختياري | DNS على منفذه القياسي. إن لم يستطع المُعدِّن الاستماع عليه، فلا يخسر إلا هذا المنفذ وحده. |

يختبر المشغّل منفذ TCP رقم 443 من الإنترنت قبل أن يُدرج موسِّعك. وتمنح منافذ UDP العملاء طرقًا أكثر للوصول إليه.

لا يستطيع الاستماع على منفذ TCP رقم 443 في الحاسوب إلا برنامج واحد. عندما تعمل عدة عمليات للمُعدِّن على مضيف واحد، مثلًا مع `--all-operators`، فإن أول عملية تأخذ المنفذ تخدم الموسِّع للمضيف كله، وتتولى عملية أخرى المهمة خلال 3 دقائق من توقفها. أما خادم الويب أو أي برنامج آخر على المنفذ 443 فيُبقي الموسِّع متوقفًا.

## فتح المنافذ

قد توجد ثلاثة جدران حماية بين الإنترنت والمُعدِّن: جدار الحاسوب نفسه، وجدار مزوّد الخدمة السحابية، وجهاز التوجيه المنزلي. يجب أن يسمح كل منها بمرور المنافذ.

### جدار حماية الحاسوب

باستخدام ufw (Ubuntu وDebian):

```bash
sudo ufw allow 443/tcp
sudo ufw allow 443/udp
sudo ufw allow 4053/udp
```

باستخدام firewalld (Fedora وRHEL وRocky وAlmaLinux):

```bash
sudo firewall-cmd --permanent --add-port=443/tcp --add-port=443/udp --add-port=4053/udp
sudo firewall-cmd --reload
```

إن كانت لديك قواعد nftables أو iptables خاصة بك، فأضف قواعد قبول للمنافذ إلى سلسلة input، قبل أي قاعدة تُسقط الحزم أو ترفضها، واحفظها كي تبقى بعد إعادة التشغيل.

تأتي صور Ubuntu في Oracle Cloud بقواعد iptables ترفض كل شيء عدا SSH. أدرج قواعد القبول فوق قاعدة الرفض، ثم احفظها:

```bash
sudo iptables -I INPUT -p tcp --dport 443 -j ACCEPT
sudo iptables -I INPUT -p udp --dport 443 -j ACCEPT
sudo iptables -I INPUT -p udp --dport 4053 -j ACCEPT
sudo netfilter-persistent save
```

لـ IPv6، شغّل القواعد نفسها باستخدام `ip6tables`.

على macOS وWindows، إن كان جدار الحماية مفعّلًا، فاسمح بالاتصالات الواردة للمُعدِّن (`provider`، أو `urnetwork` من مُثبِّت) عندما يسأل.

### جدران الحماية السحابية ومجموعات الأمان

عادةً ما يكون أمام الخادم السحابي جدار حماية أيضًا. اسمح بالوارد على TCP 443 وUDP 443 وUDP 4053 من `0.0.0.0/0` و`::/0`:

- **AWS:** مجموعة الأمان الخاصة بالمثيل (القواعد الواردة)، وقائمة التحكم في الوصول الشبكي (ACL) للشبكة الفرعية إن كنت قد غيّرتها.
- **Google Cloud:** قاعدة جدار حماية VPC للدخول تنطبق على المثيل.
- **Azure:** مجموعة أمان الشبكة على واجهة الشبكة للآلة الافتراضية أو على شبكتها الفرعية.
- **Oracle Cloud:** قائمة الأمان في VCN أو مجموعة أمان الشبكة، إضافة إلى قواعد iptables أعلاه.
- **Hetzner Cloud:** جدار Cloud Firewall، إن كان مرفقًا بالخادم.
- **DigitalOcean:** جدار Cloud Firewall، إن كان مرفقًا بالـ Droplet.

### أجهزة التوجيه المنزلية

في المنزل، يمنع جهاز التوجيه الاتصالات الواردة. في إعداداته (التي تُسمّى غالبًا إعادة توجيه المنافذ أو الخوادم الافتراضية أو NAT)، أعد توجيه TCP 443 وUDP 443 وUDP 4053 إلى الحاسوب الذي يشغّل المُعدِّن. امنح ذلك الحاسوب عنوانًا ثابتًا في شبكتك (حجز DHCP)، كي تظل إعادة التوجيه تشير إليه. لا يمكن أن يحصل على المنفذ 443 إلا حاسوب واحد خلف عنوان IPv4 عام.

بعض الاتصالات لا يمكن إعادة توجيهها. إن كان عنوان جهاز التوجيه على الإنترنت (WAN) بين `100.64.0.0` و`100.127.255.255`، أو لم يكن العنوان الذي تراه المواقع لك، فإن مزوّد الإنترنت يضعك خلف NAT على مستوى المزوّد (CGNAT). اطلب من مزوّدك عنوان IPv4 عامًا، أو استخدم IPv6.

تمنح أجهزة توجيه كثيرة كل جهاز عنوان IPv6 عامًا لكنها تحظر اتصالات IPv6 الواردة. اسمح بالوارد على TCP 443 وUDP 443 وUDP 4053 إلى هذا الحاسوب في جدار حماية IPv6 لجهاز التوجيه.

### Docker

يحتاج المُعدِّن داخل حاوية إلى نشر منافذه:

```bash
docker run -p 443:443/tcp -p 443:443/udp -p 4053:4053/udp …
```

لا تزال جدران الحماية أعلاه تنطبق على المضيف.

## Linux: اسمح للمُعدِّن بالاستماع على المنفذ 443

لا يسمح Linux بالاستماع على المنافذ الأدنى من 1024 إلا للبرامج ذات الامتيازات. يشغّل المُثبِّت و`provider service install` المُعدِّن باسم مستخدمك، لذا لا يستطيع موسِّعه الاستماع على منفذ TCP رقم 443 ويبقى متوقفًا. يقول السجل حينها `tcp_443_permission_denied`. أما المُعدِّن الذي يعمل أصلًا بصلاحيات root، مثل الذي ثُبّت باستخدام `sudo provider service install --system`، أو بصلاحيات root داخل حاوية، فيستطيع ذلك. يسمح macOS وWindows لأي برنامج بالاستماع على المنفذ 443، فلا شيء يجب منحه هناك.

الحل خدمة نظام تشغّل المُعدِّن باسم مستخدمك، مع امتياز إضافي واحد: `CAP_NET_BIND_SERVICE`، الذي يتيح لبرنامج الاستماع على المنافذ الأدنى من 1024.

### باستخدام مُثبِّت Linux

شغّل المُثبِّت مجددًا مع `--system`، باسم المستخدم الذي يُعدِّن (لا باستخدام `sudo`). سيطلب كلمة مرور `sudo` مرة واحدة:

```bash
curl -fsSL https://raw.githubusercontent.com/urnetwork/connect/main/scripts/Provider_Install_Linux.sh | sh -s -- --system
```

يمكن أيضًا تحويل تثبيت موجود باستخدام `urnet-tools reinstall --system`.

يثبّت `/etc/systemd/system/urnetwork.service`، التي تشغّل المُعدِّن باسمك، ويوقف `urnetwork.service` الخاصة بك ويزيلها، ويحتفظ بمؤقّت التحديث. ومن ثم تعمل `urnet-tools start` و`stop` و`restart` و`status` و`logs` و`uninstall` على خدمة النظام، وتطلب `start` و`stop` و`uninstall` صلاحيات `sudo`.

إذا شُغّل المُثبِّت بصلاحيات root دون جلسة مستخدم لـ systemd (صدفة `sudo su`)، فإنه يثبّت خدمة النظام من تلقاء نفسه.

### باستخدام خدمة provider

```bash
sudo "$(command -v provider)" service install --system --as="$USER"
```

المسار الكامل موجود لأن `sudo` لا يبحث في `~/.local/bin`. يثبّت هذا `urnetwork-provider.service` كخدمة نظام تشغّل المُعدِّن باسم ذلك المستخدم، بملفه التنفيذي و`~/.urnetwork` الخاص به. وقبل ذلك يوقف `provider service` الخاصة بذلك المستخدم ويزيلها، كي لا يعمل مُعدِّنان بهوية واحدة أبدًا.

لا تزال التحديثات تُثبَّت تلقائيًا، وتعمل باسم ذلك المستخدم، وتعيد وحدة path صغيرة يملكها root تشغيل الخدمة بعد كل تحديث. يعرض `provider service status` الخدمة. لإزالتها:

```bash
sudo "$(command -v provider)" service uninstall --system
```

أما `sudo provider service install --system` العادي، دون `--as`، فلم يتغير: يشغّل المُعدِّن بصلاحيات root، وحالته في `/var/lib/urnetwork`.

### ما تمنحه الوحدة

وحدة المُثبِّت، لمستخدم اسمه `alice`:

```ini
[Unit]
Description=URnetwork Provider
Documentation=https://ur.xyz/docs/miner/extender
Wants=network-online.target
After=network-online.target

[Service]
User=alice
ExecStart="/home/alice/.local/share/urnetwork-provider/bin/urnetwork" provide
Restart=on-failure
RestartSec=30
AmbientCapabilities=CAP_NET_BIND_SERVICE
CapabilityBoundingSet=CAP_NET_BIND_SERVICE
NoNewPrivileges=yes

[Install]
WantedBy=multi-user.target
```

لوحدة `provider service` سطر `User=` نفسه والأسطر الثلاثة نفسها الخاصة بالقدرات، مع `ExecStart=<path>/provider start` و`Environment=URNETWORK_STATE_DIR=/home/<user>/.urnetwork`.

ثلاثة أسطر تشكّل المنح كله:

- يمنح `AmbientCapabilities=CAP_NET_BIND_SERVICE` المُعدِّن ذلك الامتياز الوحيد.
- يمنع `CapabilityBoundingSet=CAP_NET_BIND_SERVICE` حيازته أي امتياز آخر أبدًا.
- يمنع `NoNewPrivileges=yes` المُعدِّنَ، وكل ما يشغّله، من اكتساب امتيازات، مثلًا عبر برنامج setuid.

المقايضة: ما دامت الخدمة تعمل، يستطيع البرنامج الذي تشغّله الاستماع على المنافذ الأدنى من 1024. يوجد الملف التنفيذي في مجلدك، لذا يستطيع أي أحد يقدر على استبداله (أنت، أو برنامج يعمل باسمك) تشغيل شيفرة تستمع على المنافذ المنخفضة ضمن هذه الوحدة. ولا تكتسب تلك الشيفرة أي امتياز آخر: فهي لا تعمل بصلاحيات root، و`NoNewPrivileges` مفعّل، والمجموعة المحددة لا تضم إلا تلك القدرة الواحدة. إن لم يكن ذلك مقبولًا على حاسوب مشترك، فلا تستخدم `--system`. يظل المُعدِّن يُعدِّن من دون موسِّعه.

طرق أخرى لمنح المنفذ، ولماذا لا يستخدمها المُعدِّن:

- `setcap` على الملف التنفيذي: تضيع قدرات الملف في كل مرة يستبدل فيها تحديثٌ الملفَ التنفيذي.
- ملف تنفيذي setuid: امتيازات أكثر بكثير مما يحتاج إليه منفذ واحد.
- `net.ipv4.ip_unprivileged_port_start`: يغيّر القاعدة لكل برنامج ولكل مستخدم على الحاسوب.

للعودة إلى خدمة مستخدم: مع المُثبِّت، شغّل `urnet-tools uninstall`، ثم ثبّت مجددًا دون `--system` (تُحفظ هويتك في `~/.urnetwork`). ومع `provider service`، شغّل `sudo "$(command -v provider)" service uninstall --system`، ثم `provider service install`.

## التحقق منه

```bash
provider status
provider doctor
```

في `provider status` سطر **Extender**. وفي `provider doctor` سطر **Inbound 443**: هل يحوز المُعدِّن منفذ TCP رقم 443، ونتيجة آخر تفعيل له.

في السجل (`provider service logs --follow`، أو `urnet-tools logs`)، يقول سجل `extender` ما الخطأ في `reason`، وكيف تصلحه في `guidance`:

| `reason` | ما يعنيه | ما يجب فعله |
| --- | --- | --- |
| `tcp_443_permission_denied` | لا يُسمح للمُعدِّن بالاستماع على المنفذ 443. | [اسمح للمُعدِّن بالاستماع على المنفذ 443](#linux-let-the-miner-listen-on-port-443). |
| `tcp_443_in_use` | برنامج آخر يحوز منفذ TCP رقم 443: عملية مُعدِّن أخرى، أو خادم ويب. | لا يمكن أن يملكه إلا برنامج واحد في كل حاسوب. يأخذ المُعدِّن المنفذ خلال 3 دقائق من تحرّره. |
| `tcp_443_bind_failed` | فشل الاستماع على المنفذ 443 لسبب آخر. | اقرأ أسطر السجل المحيطة به. |
| `unreachable_on_tcp_443` | المُعدِّن يستمع، لكن اختبار المشغّل لم يستطع الوصول إليه من الإنترنت. | [افتح المنافذ](#open-the-ports)، ثم أعد تشغيل المُعدِّن. |

يحاول الموسِّع الذي لا يستطيع الإنترنت الوصول إليه التفعيل مجددًا مرة واحدة يوميًا. بعد فتح المنافذ، أعد تشغيل المُعدِّن للمحاولة فورًا: `provider service restart`، أو `urnet-tools restart` مع مُثبِّت.
