# Как запустить валидатор

Валидатор UR работает в **Bittensor SN25, netuid 25**. Текущий [`sn/validator`](https://github.com/urfoundation/sn/tree/main/validator) измеряет провайдеров с помощью проходов `/verify`, хранит подписанные свидетельства и отправляет полученные веса майнеров через нативный commit-reveal. Один процесс `validator` выполняет и измерение, и отправку весов.

Валидаторы получают **нативные дивиденды Bittensor**. Они не связаны с вознаграждениями провайдеров, которые забираются из расчётного хранилища UR. В выпуске 1.0 нет команды `validator claim` и нет вознаграждения за усилия валидатора. Порядок вывода средств описан ниже.

Это руководство посвящено валидатору SN25. У **корневого валидатора в netuid 0** отдельные регистрация, работа и получение вознаграждений из корзины; регистрация в root не запускает проверку UR. Про другие роли в UR читайте в [руководстве майнера](/docs/miner) и [руководстве сетевого оператора](/docs/operator).

## Перед началом

Подготовьте следующие исходные данные для развёртывания, к которому собираетесь присоединиться:

- Хост с Linux, постоянное хранилище и непрерывный доступ к HTTPS API и транспорту WSS каждого настроенного оператора, а также к конечным точкам RPC развёртывания: EVM по HTTP(S) и нативной по WS(S). Проверки долговечных томов в mainnet требуют Linux, хотя бинарный файл можно собрать и для macOS.
- Кошелёк coldkey Bittensor со средствами на регистрацию, стейкинг и комиссии за транзакции. Храните его на машине, которая используется для операций с кошельком. Работающему валидатору нужны его hotkey и клиентские ключи для каждого оператора, а не coldkey.
- Зарегистрированный в SN25 hotkey с достаточным весом стейка, чтобы получить разрешение валидатора (validator permit). Регистрация, порог стейка и число разрешений — это состояние цепочки, а не фиксированные величины этого руководства. Как определяется право на разрешение, объясняется на странице [Bittensor validator permits](https://www.bittensor.com/docs/guides/validating).
- Полная, независимо утверждённая **производственная конфигурация schema-3**, утверждения среды выполнения и политики, на которые она ссылается, а также файлы активации и истории для каждого оператора. Получите их для вашего фактического hotkey, развёртывания и путей на хосте до запуска службы.
- Подготовленные каталоги состояния и закреплённое хешем SHA-256 объявление долговечного тома для этих каталогов. Запуск в mainnet требует этого объявления и проверяет фактическую идентичность хранилища.

Текущий производственный бинарный файл принимает подготовленное развёртывание schema-3. Его команды `init --config`, `register`, `stake add`, `activate` и `status --config` всё ещё используют старый загрузчик предактивации, который отклоняет schema 3. Они не дают самостоятельно начать работу в текущем mainnet. Для регистрации и стейкинга используйте описанные ниже нативные шаги кошелька; свидетельства и утверждения для mainnet получайте через процесс начальной настройки развёртывания. Изменение номера схемы или копирование конфигурации testnet этих исходных данных не даёт. Эта граница описана в документе [допуск среды выполнения в продакшн](https://github.com/urfoundation/sn/blob/main/mainnet/VALIDATOR-PRODUCTION-RUNTIME.md).

## 1. Получение валидатора

Скачайте сборку выпуска валидатора или соберите её из исходного кода.

### Загрузка выпуска

Валидатор распространяется как `urnetwork-validator-<version>.tar.gz` на [странице выпусков build](https://github.com/urnetwork/build/releases). Архив содержит по одному бинарному файлу на платформу по пути `<os>/<arch>/validator` для Linux и macOS. Валидатор в mainnet использует бинарный файл для Linux, `linux/amd64` или `linux/arm64` (см. [Перед началом](#before-you-start)):

```bash
VERSION=2026.10.6-1065506180   # the latest tag on the releases page, without the leading v
curl -fSsL -o urnetwork-validator.tar.gz \
  "https://github.com/urnetwork/build/releases/download/v${VERSION}/urnetwork-validator-${VERSION}.tar.gz"
tar -xzf urnetwork-validator.tar.gz
install -d "$HOME/.local/bin"
install -m 755 linux/amd64/validator "$HOME/.local/bin/validator"   # choose your os/arch
"$HOME/.local/bin/validator" --help
```

Добавьте `$HOME/.local/bin` в свой `PATH` для команд ниже. Запишите версию выпуска вместе с бинарным файлом, чтобы последующее развёртывание могло её воспроизвести.

### Или сборка из исходного кода

Собирайте из ревизии `sn`, выбранной для вашего развёртывания. Используйте версию Go, объявленную в [`sn/go.mod`](https://github.com/urfoundation/sn/blob/main/go.mod), и соответствующие checkout-ы соседних репозиториев для его локальных директив `replace`: `connect` (включая `sctp`), `sdk`, `server`, `warp`, `proxy`, `userwireguard`, `glog`, `goidenticons` и `gvisor`.

Из корня репозитория `sn`:

```bash
go build -trimpath -o ./bin/validator ./cli/validator
install -d "$HOME/.local/bin"
install -m 755 ./bin/validator "$HOME/.local/bin/validator"
"$HOME/.local/bin/validator" --help
```

Добавьте `$HOME/.local/bin` в свой `PATH` для команд ниже. Исполняемая точка входа — `cli/validator`; `validator/` — импортируемая реализация, поэтому `go build ./validator` не создаёт исполняемый файл службы. Запишите ревизию исходного кода вместе с бинарным файлом, чтобы последующее развёртывание могло её воспроизвести.

## 2. Создание ключей службы

Создавайте ключи под учётной записью, которой будут принадлежать закрытые файлы валидатора, после того как администратор хоста подготовит для неё хранилище. В этом примере используются операторы `1` и `2`; подставьте фактические ID операторов и включите каждого оператора в конфигурацию вашего развёртывания:

```bash
umask 077
validator init --state_dir=/var/lib/ur-validator --no_id=1 --no_id=2
```

Команда создаёт `/var/lib/ur-validator/hotkey.seed` и `no-<id>/client.key` для каждого оператора с правами `0600`. Она выводит адрес SS58 и открытый ключ hotkey, а также открытый `vpk` каждого клиентского ключа. Существующие seed повторно используются. Hotkey — это sr25519; клиентские ключи для каждого оператора — Ed25519. Храните исходные ключи вместе с исходным состоянием при перезапусках и делайте их закрытые резервные копии. Никогда не используйте один клиентский ключ или каталог состояния для нескольких операторов или валидаторов.

Форма `init` с каталогом состояния работает до того, как появится производственная конфигурация. Если вы уже управляете зарегистрированным hotkey, подготовьте его существующий seed вместо того, чтобы создавать другую идентичность. Файл seed hotkey принимает 32 необработанных байта или 64 шестнадцатеричных символа с необязательным префиксом `0x`. Храните файлы seed клиентов для каждого оператора в том виде, в каком они созданы. Не передавайте материал seed как аргумент командной оболочки и не помещайте его в конфигурацию YAML.

## 3. Регистрация и стейк в SN25

На **машине с кошельком coldkey** установите текущий Bittensor CLI по его [официальной инструкции по установке](https://www.bittensor.com/docs/quickstart). В примерах ниже используется текущий набор команд v11; проверьте `btcli --version` и [руководство по миграции](https://www.bittensor.com/docs/migration), если в вашей установке старые флаги `--wallet.name`.

Задайте публичный адрес hotkey равным `hotkey ss58`, который вывела `validator init`, и выберите свой существующий кошелёк coldkey. Эти переменные не содержат секретов:

```bash
VALIDATOR_WALLET='your-coldkey-wallet-name'
VALIDATOR_HOTKEY='your-validator-hotkey-ss58'

btcli -n finney query subnet-hyperparameters --netuid 25 --json
btcli -n finney query metagraph --netuid 25 --json
```

Прежде чем отправлять транзакцию, проверьте текущую доступность и стоимость регистрации. Предварительно просмотрите [регистрацию](https://www.bittensor.com/docs/tx/burned-register), затем отправьте ту же операцию с подтверждением:

```bash
btcli -n finney -w "$VALIDATOR_WALLET" tx burned-register \
  --netuid 25 --hotkey "$VALIDATOR_HOTKEY" --dry-run

btcli -n finney -w "$VALIDATOR_WALLET" tx burned-register \
  --netuid 25 --hotkey "$VALIDATOR_HOTKEY"
```

Если hotkey уже зарегистрирован на нужный coldkey, сохраните эту регистрацию. Одна регистрация не даёт разрешения валидатора.

Выберите сумму TAO для стейка, исходя из текущих условий получения разрешения и доступного баланса, оставив средства на комиссии. Введите эту сумму, когда появится запрос:

```bash
read -r -p 'TAO amount to stake: ' VALIDATOR_STAKE_TAO
btcli -n finney -w "$VALIDATOR_WALLET" tx add-stake \
  --netuid 25 --hotkey "$VALIDATOR_HOTKEY" \
  --amount-tao "$VALIDATOR_STAKE_TAO" --dry-run

btcli -n finney -w "$VALIDATOR_WALLET" tx add-stake \
  --netuid 25 --hotkey "$VALIDATOR_HOTKEY" \
  --amount-tao "$VALIDATOR_STAKE_TAO"
```

[`add-stake`](https://www.bittensor.com/docs/tx/add-stake) конвертирует TAO в alpha SN25 по цене пула. Перед подтверждением проверьте в предварительном просмотре комиссии и защиту цены. После финализации и назначения разрешения снова проверьте [metagraph](https://www.bittensor.com/docs/query/metagraph): ваш hotkey, владеющий им coldkey, UID, стейк и разрешение валидатора должны совпадать с производственными исходными данными.

Бинарный файл SN также сохраняет `validator register` и `validator stake add` для конфигураций, которые допускает его старый загрузчик. По умолчанию они работают в пробном режиме, пока не указан `--apply`, принимают файл seed coldkey и выражают суммы стейка в **rao**. Они не заменяют описанную здесь настройку schema-3 для mainnet.

## 4. Аутентификация у каждого оператора

Используйте для каждого настроенного оператора отдельные учётные данные аккаунта и отдельную идентичность клиента. Для эталонного оператора получите код авторизации на [ur.io/?auth](https://ur.io/?auth), затем выполните:

```bash
validator auth --api_url=https://api.bringyour.com
install -m 600 "$HOME/.urnetwork/jwt" /var/lib/ur-validator/no-1/network.jwt
```

Для другого оператора используйте его фактический API и процесс входа, затем скопируйте только что выданный токен в каталог этого оператора. `validator auth -f --api_url=...` явно заменяет временный `$HOME/.urnetwork/jwt`; `validator auth --user_auth=... --api_url=...` вместо этого запрашивает пароль.

`validator auth --operator=<domain>` находит оператора в опубликованном [списке операторов](/operators.yml) вместо `--api_url` и записывает его токен в `<state_dir>/operators/<domain>/jwt`; каталог состояния по умолчанию — `~/.urnetwork/validator`. Именно оттуда его читает [измерение всех операторов из списка](#measure-every-listed-operator-without-weights). С `--hotkey_seed_file=<path>` команда `validator auth` выполняет вход с hotkey, как с кошельком TAO, вместо кода авторизации или пароля. Производственная конфигурация читает только те пути `network_jwt_file`, которые в ней указаны.

В конфигурации каждого оператора указываются `network_jwt_file`, `client_jwt_file` и `client_key_seed_file`. Клиентский JWT привязан к исходному клиентскому ключу и идентичности. Производственная конфигурация может явно разрешить первую регистрацию с `allow_client_registration: true`; без такого подписанного разрешения предоставьте существующие учётные данные клиента. Неподдерживаемый API регистрации, отсутствующий вход или несовпадение идентичности могут оставить измерение в ожидании. При восстановлении аутентификации сохраняйте существующую идентичность.

## 5. Подготовка производственной конфигурации и свидетельств

Используйте полный утверждённый `release.yml`, а не отредактированную вручную версию подписанной конфигурации. Ниже — перечень исходных данных для текущей [`ReleaseConfig`](https://github.com/urfoundation/sn/blob/main/validator/config.go):

| Исходные данные | Что подготовить |
| --- | --- |
| Производственная идентичность | `schema_version: 3`, `production: true`, `release: "1.0"`, `deployment_id` развёртывания и ваш ненулевой `validator_id`. |
| Сеть и контракты | Для mainnet `chain_id: 964`, `netuid: 25`, фактические `genesis_hash`, `coordinator`, `settlement_vault` и `deploy_block`. |
| Среда выполнения | Проверенные `runtime_spec`, `transaction_version`, `state_version`, `runtime_code_hash` и `runtime_metadata_hash`, а также конечные нативные окна блоков и эпох из утверждения и возможность производителя. |
| Политика и расписание | Полная `policy`, соответствующий ей `policy_hash`, `version_key`, `trail_depth`, равный глубине прохода в политике, и `poll_seconds` от 1 до 60. |
| Нативное экономическое утверждение | Независимо подписанное утверждение развёртывания `treasury_approval` или `owner_recycle_approval` с независимым публичным подписантом и точными путём, длиной в байтах и SHA-256 файла утверждения. Эти селекторы взаимоисключающие. |
| Подключения | Явные конечные точки EVM `rpc` по HTTP(S) и нативные конечные точки `substrate` по WS(S). |
| Закрытые файлы службы | `state_dir`, `hotkey_seed_file` и отдельные состояние и учётные данные для каждого оператора. |
| Каталог операторов | Для каждого оператора `no_id`, `api_url`, `connect_url`, отдельный `artifact_signer`, пути к учётным данным и ключам и `concurrency`. Включите не меньше `policy.safety.minimum_healthy_no_count` операторов. |
| Независимость | `controlled_no_ids` перечисляет операторов, которыми вы управляете, чтобы их пулы и связанные с ними флоты верхнего уровня были скрыты. |
| Свидетельства | Полные границы `evidence_v2` и для каждого оператора `activation`, `vpk_signature`, `hotkey_signature`, `context`, `history`, `replay_scratch_root` и `seal_scratch_root`. Ссылки на файлы закрепляют путь, байты и SHA-256. |
| Исходные свидетельства запросов | `request_receipt_scope` и `request_preparation` развёртывания для операторов, использующих исходный процесс квитанций запросов, с их подготовленным хранилищем. |
| История обновлений | Все выбранные `production_runtime_approvals`, `production_authority_history` и ревизия ёмкости, необходимые для повторного воспроизведения существующей работы под её исходными полномочиями. |

Текущий производственный путь казначейства и формат его утверждения описаны в документе [нативное казначейство в продакшне](https://github.com/urfoundation/sn/blob/main/validator/TREASURY-PRODUCTION.md). Валидаторы получают публичные данные маршрутизации казначейства; закрытый ключ казначейства для валидатора не требуется.

Подбирайте размер хоста под утверждённые границы свидетельств и истории и под все настроенные обработчики проходов. `concurrency` для каждого оператора должен быть от 1 до 128, не превышать лимит активных проходов политики и позволять каждому обработчику пройти ограниченный по частоте шлюз seed до тайм-аута шага. Увеличение `concurrency` или границ диска в подписанной конфигурации требует утверждённой замены.

Записи активации связывают идентичность клиента каждого оператора с вашим зарегистрированным hotkey валидатора — с обеими подписями и с финализированной публикацией в журнале свидетельств. Их контекст и история должны охватывать настроенную начальную границу расчётов. Производственная служба проверяет подлинность этих исходных данных, прежде чем начинать новую работу. Пустой записи `evidence_v2.operators` в mainnet недостаточно. Старый путь `validator activate --config=...` не может сформировать эти исходные данные из конфигурации schema-3.

При подготовке сохраняйте пути неизменными. Относительные пути разрешаются относительно каталога конфигурации, и перемещение конфигурации может изменить их смысл. Типичная структура:

```text
/etc/ur-validator/
  release.yml                    # complete approved production config
  durable-volumes.json           # declaration for this host's actual storage
  approvals/                     # referenced public approval/history files
/var/lib/ur-validator/
  hotkey.seed                     # private sr25519 seed
  state/                         # durable intents and shared validator state
  no-1/
    client.key                   # private Ed25519 seed
    network.jwt
    client.jwt
    ...                          # prepared operator evidence/state
  no-2/                          # separate keys, JWTs and state
  evidence-v2/                   # prepared, hash-pinned activation inputs
  scratch-v2/                    # prepared replay and seal storage
/var/lib/ur-validator-observation/
  progress.json                  # created by the running validator
```

Это примеры путей, а не замена путям из вашего утверждённого пакета. Закрытым файлам нужны защищённые владелец и права доступа; каталоги протокола должны использовать подготовленное долговечное хранилище. Одно лишь создание пустых каталогов не подготавливает журналы попыток и не заменяет сохранённую в них историю. Разместите файл прогресса вне всех каталогов протокола, ключей, учётных данных и свидетельств, в существующем родительском каталоге, который не доступен для записи группе или другим пользователям.

## 6. Запуск и мониторинг валидатора

Задайте **независимо принятый SHA-256** объявления долговечного тома; не подставляйте заново вычисленный хеш, чтобы обойти несовпадение. Перед запуском проверьте подготовленные каталоги:

```bash
VALIDATOR_VOLUMES_SHA256='sha256:replace-with-the-approved-64-hex-digit-digest'

validator storage-inspect \
  --durable-volumes=/etc/ur-validator/durable-volumes.json \
  --durable-volumes-sha256="$VALIDATOR_VOLUMES_SHA256" \
  --directory=/var/lib/ur-validator/state \
  --directory=/var/lib/ur-validator/no-1 \
  --directory=/var/lib/ur-validator/no-2

validator run --config=/etc/ur-validator/release.yml \
  --durable-volumes=/etc/ur-validator/durable-volumes.json \
  --durable-volumes-sha256="$VALIDATOR_VOLUMES_SHA256" \
  --progress-file=/var/lib/ur-validator-observation/progress.json \
  --operators-refresh=1h
```

Команда на переднем плане выполняет реальную проверку и может отправлять веса, как только выполнены утверждённые условия. Запускайте ровно один процесс на каждый hotkey и пространство имён состояния. Используйте те же аргументы под менеджером служб вашего развёртывания; при перезапуске сохраняйте исходные журналы и подписанные ожидающие транзакции. Отказ, связанный с хранением средств или конфигурацией, разбирайте до перезапуска, а не удаляйте состояние и не создавайте ключи на замену.

`--operators-refresh=1h` отслеживает опубликованный [список операторов](/operators.yml) и загружает его заново каждый час, не меняя того, что валидатор подписывает и взвешивает: взвешиваются только операторы, закреплённые в подписанной конфигурации, и выпуск работает ровно так же, как без этого флага. Список кешируется как `operators.yml` в `state_dir` конфигурации. При запуске и при каждом изменении списка валидатор записывает в журнал отчёт о расхождениях и сохраняет его в `operators-report.json` рядом с этим кешем. Отчёт показывает каждого закреплённого оператора, сопоставленного со списком по URL API, как присутствующего в списке или исключённого из него, с указанием несовпадения URL подключения, если оно есть, а также каждого оператора из списка, которого конфигурация не закрепляет. Это служебный вывод; обратно его ничто не читает.

С `--operators-refresh` параметр `--operators-url=<url>` отслеживает другой список, а `--observe-unpinned-operators` дополнительно измеряет каждого оператора из списка, которого конфигурация не закрепляет, — только для наблюдения, в `observed-operators/<domain>/` внутри `state_dir` конфигурации. Наблюдение выполняет вход и подготовку с `hotkey_seed_file` конфигурации, и его результаты никогда не попадают в веса, свидетельства или производственное состояние. Закреплённые операторы сохраняют свой настроенный `network_jwt_file`; если он отсутствует, об этом сообщается, но он никогда не создаётся.

Следите за stderr и ограниченной по размеру [записью прогресса](https://github.com/urfoundation/sn/blob/main/mainnet/SERVICE-PROGRESS.md). Проверяйте несколько отдельных сигналов:

- Свежие `heartbeat_at` и `publisher.last_success_at` показывают активность процесса и публикации.
- Записи `intent` показывают границы подготовленных, финализированных и применённых транзакций. Отправленная или ожидающая транзакция — это ещё не применённый вектор весов.
- `settlement` показывает долговечный курсор эпох и незавершённую работу по публикации.
- Диагностика аутентификации у операторов и проходов показывает, может ли продвигаться измерение по каждому оператору.
- Расхождений со списком операторов в записи прогресса нет. С `--operators-refresh` они есть в журнале и в `operators-report.json`.
- Нативные чтения metagraph показывают, сохраняет ли hotkey свой UID и разрешение и получает ли дивиденды.

Ожидание эпохи может быть нормальным; один лишь свежий heartbeat не доказывает успешную проверку. Текущая `validator status --config` отклоняет schema 3, поэтому для этого производственного пути используйте запись прогресса, журналы службы и нативные чтения цепочки. Без `--config` команда `validator run` работает в устаревшем режиме только измерения и никогда не записывает веса выпуска.

### Измерение всех операторов из списка без весов

`validator run --all-operators` измеряет всех операторов из опубликованного списка операторов и никогда не записывает веса. У каждого оператора своё состояние в `<state_dir>/operators/<domain>/`: токен `jwt`, ключ измерения `.validator.key` и клиентский JWT `.validator.jwt`. Состояние для одного оператора, `<state_dir>/.validator.key` и `~/.urnetwork/jwt`, не используется.

```bash
validator run --all-operators --auto-register \
  --hotkey_seed_file=/absolute/private/hotkey.seed
```

- `--auto-register` выполняет вход с hotkey, как с кошельком TAO, там, где у оператора нет токена. Он создаёт идентичность измерения только для совершенно нового каталога оператора и никогда не восстанавливает, не присваивает и не заменяет существующую идентичность. Файл seed должен уже существовать; он никогда не создаётся.
- Без `--auto-register` оператор без токена записывает в журнал `operator <domain> is awaiting auth: validator auth --operator=<domain>` и проверяется снова каждые пять минут. Каталог без идентичности измерения отклоняется и пробуется снова, а в журнале указываются флаги, которые её создают.
- Список кешируется как `<state_dir>/operators.yml` и загружается заново каждый час или с интервалом `--operators-refresh` — длительностью в формате Go не меньше `1m`. `--operators-url=<url>` отслеживает другой список. Пока список не удаётся загрузить, используется последняя исправная копия.
- Новый оператор в списке запускается, исключённый из списка останавливается с сохранением состояния, а оператор, у которого изменились URL-адреса, перезапускается. Сбойный оператор перезапускается через 30 секунд, с удвоением интервала до 10 минут, и никогда не останавливает остальных.

## 7. Получение вознаграждений валидатора

Дивиденды валидатора SN25 начисляются через нативный учёт стейкинга Bittensor. Ваш coldkey управляет вашей собственной позицией; делегированный стейк и его вознаграждения принадлежат делегирующим coldkey, за вычетом доли валидатора. Координатор и расчётное хранилище UR не хранят дивиденды валидаторов. `provider claim`, `snclaim submit` и Merkle-доказательства выплат оператора предназначены для пути вознаграждений майнеров и провайдеров.

Чтобы вернуть доступные alpha SN25 в **свободные TAO**, выведите выбранную сумму из стейка того hotkey, на котором фактически находится эта позиция. Используйте машину с кошельком coldkey и те же публичные переменные кошелька, что и в шаге 3. Сначала проверьте свои позиции и выберите сумму в **alpha**, а не в TAO:

```bash
btcli -n finney -w "$VALIDATOR_WALLET" stake list
btcli -n finney -w "$VALIDATOR_WALLET" wallet balance
read -r -p 'SN25 alpha amount to withdraw: ' VALIDATOR_WITHDRAW_ALPHA

btcli -n finney query quote-unstake \
  --netuid 25 --amount-alpha "$VALIDATOR_WITHDRAW_ALPHA" --json

btcli -n finney -w "$VALIDATOR_WALLET" tx remove-stake \
  --netuid 25 --hotkey "$VALIDATOR_HOTKEY" \
  --amount-alpha "$VALIDATOR_WITHDRAW_ALPHA" --dry-run
```

[Котировка](https://www.bittensor.com/docs/query/quote-unstake) оценивает выход в TAO, комиссии и проскальзывание. Проверив пробный запуск и оставшийся стейк, отправьте транзакцию с интерактивным подтверждением:

```bash
btcli -n finney -w "$VALIDATOR_WALLET" tx remove-stake \
  --netuid 25 --hotkey "$VALIDATOR_HOTKEY" \
  --amount-alpha "$VALIDATOR_WITHDRAW_ALPHA"

btcli -n finney -w "$VALIDATOR_WALLET" stake list
btcli -n finney -w "$VALIDATOR_WALLET" wallet balance
```

[`remove-stake`](https://www.bittensor.com/docs/tx/remove-stake) обменивает доступные alpha на TAO и зачисляет их на свободный баланс подписывающего coldkey. Проверьте результат финализированной транзакции и обновлённые балансы. Накопленная позиция содержит как основную сумму, так и вознаграждения: отдельного баланса SN25 «забрать только мой заработок» нет. Вывод стейка может повлиять на ваше разрешение; блокировки, залог, комиссии и защита цены пула могут ограничить операцию. Если ваши вознаграждения направлялись на другой hotkey для стейкинга, выберите фактическую позицию.

**Вознаграждения root устроены иначе.** Если вы также стейкаете в netuid 0, для доходности его корзины перед выводом существует отдельный нативный процесс получения из root. Следуйте [инструкциям Bittensor по стейкингу в root и дивидендам](https://www.bittensor.com/docs/guides/staking#root-stake-and-dividends). Не используйте получение из root для сбора обычных вознаграждений alpha SN25.
